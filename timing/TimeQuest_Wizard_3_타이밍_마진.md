# 타이밍 마진(Timing Margin) 정리

> 앞선 문서 ①(16MUX 조합회로), ②(FF 순차회로)의 후속 자료.
> 목표: Slack과 마진의 차이를 이해하고, 시스템 종류별로 어느 정도의 마진이 필요한지 감을 잡는다.

---

## 1. 마진이란

**Slack(여유)** 은 STA(정적 타이밍 분석)가 계산하는 값이고,
**마진**은 Slack 위에 설계자가 **일부러 더 확보하는 여유**이다.

```
Setup Slack = (요구 시간: 캡처 에지 − tsu) − (실제 도착 시간)
Hold  Slack = (실제 도착 시간) − (요구 시간: 캡처 에지 + th)

Slack ≥ 0           →  툴 기준 "통과"
Slack ≥ 0 + 마진    →  실제 제품에서 "안심할 수 있는" 상태
```

Slack이 0.001 ns 이상이면 툴은 통과로 보지만, 제품은 그 상태로 출시하면 안 된다.
툴이 모르는 변동이 남아 있기 때문이다.

---

## 2. 마진이 필요한 이유

| 원인 | 설명 |
|---|---|
| **PVT 변동** | 공정(Process), 전압(Voltage), 온도(Temperature)에 따라 지연이 크게 변함 |
| **클럭 지터·스큐** | 클럭 에지가 이상적인 위치에 오지 않음 |
| **OCV** | 같은 칩 안에서도 위치별로 지연이 다름 |
| **노화(Aging)** | 수년 사용하면 트랜지스터가 느려짐 (NBTI, HCI) |
| **크로스토크·전원 노이즈** | 옆 신호나 IR drop 때문에 지연이 변함 |
| **모델·제약 오차** | SDC에 넣은 tsu/tco/보드 지연 값이 실제와 다름 |
| **설계 변경** | 나중에 로직이 추가되면 배치·배선이 바뀌어 타이밍이 달라짐 |

---

## 3. FPGA에서의 마진 (Quartus / TimeQuest 기준)

### 3-1. 코너를 모두 확인한다

Cyclone II는 Slow(고온·저전압), Slow(저온), Fast 모델이 있다.

| 분석 | 가장 위험한 코너 |
|---|---|
| **Setup** | Slow 모델 |
| **Hold** | Fast 모델 |

TimeQuest에서 `Report Timing`을 **Slow와 Fast 모델 모두**로 돌려야 한다.

### 3-2. 실무 목표치 (경험칙)

| 항목 | 최소 | 권장 |
|---|---|---|
| Setup Slack (Slow 코너) | ≥ 0 | 클럭 주기의 **5~10%** 이상 |
| Hold Slack (Fast 코너) | ≥ 0 | **0.1~0.3 ns** 이상 |
| Fmax | 목표 주파수 이상 | 목표 대비 **10~20%** 높게 |

### 3-3. 100 MHz 예제(문서 ②)에 적용하면

- 주기 10 ns → Setup Slack **0.5~1.0 ns 이상**을 목표로 한다.
- Fmax 리포트가 **120 MHz 이상**이면 20% 여유가 있는 셈이다.

### 3-4. FPGA 특유의 주의점

- **자원 사용률이 80~90%를 넘으면** 배선이 길어져 타이밍이 급격히 나빠진다. 컴파일 결과가 매번 달라지기도 한다(Seed 의존).
- 마진이 작으면 **로직을 하나 추가했을 때 갑자기 위반**이 난다. 마진은 설계 변경에 대한 보험이기도 하다.
- 출력 직전 FF를 **I/O 셀 레지스터**로 강제하면 tco가 안정된다.
- 클럭 도메인 교차(CDC)는 마진으로 해결되지 않는다. **동기화 회로(2-FF 등)** 가 필요하다.

## 4. ASIC/SoC에서의 마진 (참고)

| 구분 | 일반적인 경험칙 |
|---|---|
| Clock uncertainty (setup) | 주기의 약 **5~10%** 또는 지터+스큐 합산 (수십~백수십 ps) |
| Clock uncertainty (hold) | 수십 ps 수준 |
| OCV / AOCV / POCV derate | 약 **3~10%** (공정 미세할수록 큼) |
| 설계 초반 목표 | 최종 사인오프보다 **10~20% 더 빡빡하게** 잡고 시작 |
| 사인오프 | 모든 PVT 코너·모드에서 Slack ≥ 0, 실제로는 소량의 추가 마진 확보 |

> ⚠️ 회사·파운드리·공정마다 규칙이 다르다. 위 수치는 **경험칙**이지 표준이 아니므로,
> 실제 프로젝트에서는 파운드리 사인오프 가이드와 팀 규정을 우선한다.

## 5. 시스템 종류별로 필요한 마진

| 시스템 | 동작 환경 | 마진 수준 | 이유 |
|---|---|---|---|
| **일반 소비자 제품** | 0~70℃, 수명 짧음 | 보통 (Setup 5% 내외) | 비용·성능 균형 |
| **산업용** | −40~85℃(105℃), 수명 10년 이상 | 큼 | 온도 범위가 넓음, 현장 수리 어려움 |
| **자동차 (AEC-Q100)** | −40~125/150℃, 15년 이상 | 매우 큼 + **노화 derate 필수** | 안전 요구, 고온·진동·장수명 |
| **의료기기** | 환경은 온화하나 신뢰성 요구 높음 | 큼 | 오동작이 환자 안전과 직결, 인증 대응 |
| **방산·항공·우주** | 넓은 온도, 진동, 방사선 | **가장 큼** (일부 프로그램은 20~30% 이상 요구) | 임무 중 재시동·수리 불가, 방사선으로 인한 지연 변화 |
| **고속 인터페이스 (DDR, SerDes)** | 데이터 유효 구간(Eye)이 매우 짧음 | 규격의 **타이밍 버짓** 항목별 계산 | 마진이 ps 단위, UI(Unit Interval) 대비 %로 관리 |
| **저속 제어 시스템** | 주기가 길어 기본 여유가 큼 | 상대적으로 작아도 OK | 다만 CDC·비동기 입력은 별도 확인 |

> 방산·우주 등은 **고객이나 프로그램 문서에 "Slack 최소 ○○%" 같은 규정이 명시**되는 경우가 많다.
> 계약·사양서를 먼저 확인하는 것이 정답이다.

## 6. 마진을 확보하는 실전 방법

1. **파이프라인 추가** — 긴 조합 경로 사이에 FF를 넣어 한 주기에 해야 할 일을 줄인다.
2. **로직 단순화·리타이밍** — 합성 옵션(Retiming), 리소스 공유 해제 등으로 경로를 짧게 만든다.
3. **제약을 약간 빡빡하게** — 실제 목표가 100 MHz라면 SDC에 **105~110 MHz(주기 9~9.5 ns)** 로 넣고 컴파일하면 자연스러운 마진이 생긴다.
4. **Clock uncertainty 명시** — 지원되는 디바이스는 `derive_clock_uncertainty`를 쓰고, Cyclone II처럼 미지원이면 `set_clock_uncertainty`로 수동 지정한다.
5. **Seed·최적화 옵션 변경** — Fitter Seed를 바꿔 여러 번 돌려 편차를 본다. 편차가 크면 마진이 부족한 설계이다.
6. **I/O 제약 현실화** — 보드 트레이스 지연·상대 칩의 tsu/th를 반영해 tsu/th, tco 값을 보수적으로 입력한다.
7. **여러 번 컴파일해도 안정적인지 확인** — 한 번 통과한 것으로 끝내지 말고, 다른 시드에서도 통과하는지 본다.

## 7. SDC에 마진 반영하기 (문서 ②의 100 MHz 예제 확장)

문서 ②의 위저드 결과에 아래 줄을 **SDC 파일에 직접 추가**하면 마진이 반영된다.
(위저드 화면에서는 입력할 수 없고, SDC 에디터나 텍스트 편집기로 추가한다.)

```tcl
# 클럭 정의 (위저드 생성분)
create_clock -name clk -period 10.000 -waveform { 0.000 5.000 } [get_ports {clk}]

# ── 방법 A: 클럭 불확실성으로 마진 확보 (Cyclone II 등 derive_clock_uncertainty 미지원 시) ──
set_clock_uncertainty -setup 0.500 [get_clocks {clk}]   ;# setup 쪽 0.5 ns (주기의 5%)
set_clock_uncertainty -hold  0.100 [get_clocks {clk}]   ;# hold 쪽 0.1 ns

# ── 방법 B: 주기를 더 빡빡하게 (목표 100 MHz → 약 105 MHz로 제약) ──
# create_clock -name clk -period 9.500 -waveform { 0.000 4.750 } [get_ports {clk}]
```

| 방법 | 효과 | 특징 |
|---|---|---|
| A. `set_clock_uncertainty` | setup/hold에 각각 지정한 만큼 Slack을 깎아서 계산 | 마진 의도를 SDC에 **명시적으로 기록**할 수 있음 |
| B. 주기 단축 | 더 높은 주파수로 맞추도록 Fitter가 노력 | 간단하지만 의도가 코드에 드러나지 않음 |

> 방법 A와 B를 동시에 과하게 쓰면 지나치게 빡빡해져 Fitter가 불필요하게 자원을 쓰거나
> 수렴하지 못할 수 있다. 하나를 선택하고, 필요할 때만 조금씩 조정한다.
> 위 수치는 설명용 예시이며, 프로젝트 사양에 맞게 정한다.

---

## 8. 확인 체크리스트

- [ ] Slow 코너 Setup Slack이 목표 마진 이상인가?
- [ ] **Fast 코너 Hold Slack**이 0 이상, 권장 0.1~0.3 ns 이상인가?
- [ ] Fmax가 목표 주파수보다 10~20% 높은가?
- [ ] Report Unconstrained Paths에 **누락된 포트·경로**가 없는가?
- [ ] 다른 Fitter Seed로 돌려도 통과하는가?
- [ ] 자원 사용률이 과도하지 않은가? (80~90% 초과 시 주의)
- [ ] I/O 제약값(tsu/th/tco)이 실제 보드·상대 칩 사양을 반영하는가?
- [ ] 고객·프로그램이 요구하는 **최소 Slack 규정**이 있다면 충족하는가?

---

## 9. 한 장 요약

- Slack ≥ 0은 **최소 조건**이고, 제품에는 **그 위에 마진**이 필요하다.
- FPGA에서는 **Setup 5~10% / Hold 0.1~0.3 ns / Fmax 10~20% 여유**가 흔한 출발점이다.
- 환경이 가혹하고 수명이 길수록(자동차, 방산, 우주) 마진을 더 크게 잡는다.
- 숫자는 모두 경험칙이므로 **고객 사양서·팀 규정·디바이스 데이터시트**가 항상 우선한다.
